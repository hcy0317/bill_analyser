标记说明

confirmed current-state fact 表示已经从当前仓库代码或项目文档里确认的现状，不是理想设计。

investigation hint 表示人工排查时优先看的线索、对照点或可复现观察方法。

high-risk boundary 表示字段、单位、语义或层级最容易错位的位置，修 bug 时要先对齐合同。

本文以当前主链路为准：Rust HTTP runtime、PostgreSQL import staging、前端 server-paged preview。旧链路或 legacy sidecar 不作为运行时主链。

一次导入从文件到正式交易的主流程

前端选择账单并调用解析入口

confirmed current-state fact 导入入口走 /api/bills/import/v2/parse 或 /api/bills/import/v2/parse_generic，multipart 文件、JSON 和 generic JSON 分别进入对应 runtime handler。

investigation hint 如果“文件能上传但预览为空”，先看响应里是否已经有 session_id、parser summary、标准行数量，再决定查 parser 还是 stage2。

parser 把原始账单规整成标准账单

confirmed current-state fact parser 先产出 RawBill，再归一到 StandardBill。目前 registry 包含 wechat、alipay、icbc、cmbc、abc、ccb。

high-risk boundary StandardBill.amount 是 Money，序列化表现是元；后续 preview typed column 使用分。金额异常必须沿“元到分”逐层核对。

解析结果进入 import session 与 parser template 暂存

confirmed current-state fact parser 标准行会落入 import staging，形成 session、source、template、standard-row 这组导入暂存上下文。

investigation hint 如果 parser UI 看起来对，但 stage2 以后字段丢失，重点查 ImportParserTemplateDraft 到 dedup_bill_from_parser_template 的字段映射。

stage2 处理去重、转账识别和正式账单物化基线

confirmed current-state fact stage2 会加载模板、执行 smart dedup、加载标准行和历史候选、构造历史重复与转账计划，再生成 preview draft。

high-risk boundary 同批次重复、历史重复、转账识别与正式 bill materialization 共享金额、日期、账户、交易类型；任何一个字段错位都会影响后面的 signal 和确认入库。

智能链路补全分类、周期、学习、LLM、账户识别

confirmed current-state fact 处理顺序是 category rules / built-in fallback、recurring projection、learning vector recall、LLM 或推荐数据、最后 account recognition。

high-risk boundary account recognition 必须在分类、周期、学习这些 projection 之后，因为它依赖前面规整出的业务信号。提前跑会导致账户错配或覆盖用户编辑。

preview draft 被校验并写入 typed columns 与 JSON payload

confirmed current-state fact 写入 import_preview_rows 前会执行 identity validation，生成 typed columns 与 preview_payload 双份表示。

high-risk boundary typed columns 用于分页、筛选、facet、confirm；payload 用于前端展示和补充信号。两边不一致时，页面和入库可能表现不同。

前端预览页加载 server-paged rows 并转换为 ImportTransaction

confirmed current-state fact 前端 ImportPreviewRecord 通过 importPreviewTransaction.ts 映射为 ImportTransaction，再进入校验、筛选、编辑和确认 UI。

investigation hint 如果接口数据正确但页面展示错，优先查 resolveImportPreviewCategoryId、金额 cents 规范化、account/category map 是否来自当前用户。

用户编辑、重新分类、LLM 推荐或筛选选择

confirmed current-state fact 单行编辑走 preview update；重新分类会应用用户 patch 后重跑 intelligence chain；LLM preview recommend 有独立 accept/reject 入口。

high-risk boundary 用户显式编辑后的字段不能被后台推荐静默覆盖。看到“刚改完又变回去”，要查 patch 后重跑链路是否尊重 manual annotation 和 clear decision keys。

确认入库前再次校验，选中行转换为正式 bill create fields

confirmed current-state fact 后端 confirm 兼容 selected_ids，当前前端主路径主要提交 preview_updates 并保留未补丁选择集；后端会在事务内把 selected preview 转为正式账单，并更新 session 状态。

high-risk boundary confirm 会拒绝 identity validation error 或仍需 review 的行。若前端显示可确认但后端拒绝，查 preview typed columns 与 payload 的校验状态是否同步。

可疑边界和常见错位点

金额单位边界

high-risk boundary parser 的 Money 是元语义，preview 和正式 bills 多数使用 cents。

investigation hint 金额错 100 倍时沿 parser_amount -> preview_amount_cents -> amount_cents -> sourceAmountCents 对照。

分类 id 与名称边界

high-risk boundary category_id 是权威字段，preview_main_category 和 preview_sub_category 是显示与兼容信息。

investigation hint 名称对、id 空或非法时，不要用名称反推入库；先修 id 来源和 identity validation。

账户 id 边界

high-risk boundary source account、destination account、payment method 是三种不同语义。

investigation hint 微信/支付宝支付方式看起来像账户名，但前端 originalSourceAccountName 当前来自 preview_payment_method。

typed column 与 payload 边界

high-risk boundary 后端筛选、facet、confirm 倾向 typed columns；前端展示和信号细节还依赖 payload。

investigation hint 一行编辑后立刻查两边是否都变了，尤其 category、account、amount、type、selected。

server-paged 与本地筛选边界

high-risk boundary server-paged 模式下，后端才是分页和筛选真源。

investigation hint 筛选结果异常时，同时对照后端 query 参数、facet 计数、前端 fallback filter。

用户编辑与智能链路边界

high-risk boundary 用户 patch 应该拥有更高优先级，不能被规则、学习或 LLM 静默覆盖。

investigation hint 查 isManuallyAnnotated、manual annotation payload、clear decision keys 和 reclassify 后的 batch update。

转账与投资边界

high-risk boundary 转账/投资比普通收支多一个 destination account 和 destination amount。

investigation hint destination 缺失、同账户、金额方向不一致都会让 confirm 拒绝或 requires review。

历史重复与同批重复边界

high-risk boundary 同批重复、历史重复、转账 materialization 都可能写入 signal 和 dedup source ids。

investigation hint 行被误判重复时，先看 dedup 输入字段是否一致，再看阈值和历史候选集合。

当前用户数据边界

high-risk boundary category 和 account 必须属于当前用户且处于 active 范围。

investigation hint 出现跨用户 id 或历史已删除 id，应从 identity validation 层查，不要只在 UI 隐藏警告。

人工核对清单

导入前后抽样核对

  1. 选一条有明确交易时间、金额、商户的账单，记录 parser 原始字段。
  2. 核对 StandardBill.amount 与平台金额是否同单位、同符号语义。
  3. 核对 parser_amount 到 preview_amount_cents 是否只发生一次元转分。
  4. 核对 category_id 是否属于当前用户 taxonomy，名称只是辅助。
  5. 核对 source account 与 payment method 是否被混用。
  6. 如果是转账，核对 source、destination、destination amount 和 same-account validation。
  7. 编辑一行后刷新预览页，确认 typed columns 与 payload 都持久化。
  8. 确认入库后，对照正式 bills 的 amount、category_id、source_account_id、destination_account_id。

筛选和分页核对

  1. 在 server-paged 模式下核对筛选参数是否进入 getImportPreviewPage。
  2. 分类筛选分别测试正常分类、__none__、__invalid__。
  3. 账户筛选分别测试 source、destination、缺失、非法。
  4. signal 筛选逐项测试 parser、platform duplicate、transfer、history、learning、LLM。
  5. 只选中几行后翻页，确认 selected 状态来自后端而不是本地旧数组。
  6. 批量编辑或重新分类后，重新拉 page 和 facets，检查计数是否同步变化。
  7. confirm 前后对比 session status，避免已确认 session 还能被继续编辑。
修 bug 前的最低证据： 至少固定一条 preview row 的 id 或 page_sort_key，同时拿到 parser 标准行、preview typed columns、preview payload、前端转换后的 ImportTransaction、confirm 后正式 bill 五个视角。没有这五个视角，字段错位很容易被修到错误层。
快速二分方法： 如果接口返回已经错，查 Rust parser/stage2/preview 写入；如果接口正确但 UI 错，查前端转换、当前 taxonomy/account map 和本地筛选；如果 UI 正确但 confirm 错，查 confirm 重新加载、identity validation 和 bill create fields。

修复时不应破坏的合同

  1. confirmed current-state fact 导入主链是 Rust parser-first，不要新增 sidecar 或旧式透传作为运行时兜底。
  2. confirmed current-state fact category_id 和 account id 必须以当前用户 active 数据为准，非法值要在 identity validation 层处理。
  3. confirmed current-state fact preview typed columns 与 preview_payload 都是有效合同；修一个字段时要确认两边是否都需要更新。
  4. confirmed current-state fact confirm 只信任后端重新加载并校验后的 selected preview rows。
  5. high-risk boundary 金额字段改动必须人工复核元/分转换，不要只看页面显示。
  6. high-risk boundary 用户手动编辑、人工标注和 reject/accept decision 不能被重新分类链路静默覆盖。
  7. high-risk boundary 转账和投资必须同时维护 source、destination、destination amount 与同账户校验。
  8. investigation hint 每次修导入预览 bug 后，至少用一条真实 preview row 验证 parse -> stage2 -> preview -> edit/filter -> confirm 的闭环。
维护提示：后续修改导入链路、preview schema、前端 ImportTransaction 映射、筛选语义或 confirm 逻辑时，应同步更新本文相应章节。
